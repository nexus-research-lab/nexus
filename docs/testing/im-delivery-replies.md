## 开发测试库迁移注意事项

合入最新 main 后，IM 迁移编号为 `00141`；`00138` 至 `00140` 属于 Team 迁移。曾运行未合并 IM 分支、将 IM 迁移登记为 `00138` 的开发库不能直接按正式迁移序列升级。应先停止所有访问该库的后端、备份并核对实际表结构与 Goose 记录，再制定一次性的开发库迁移步骤；不要删除业务数据或在线修改迁移记录。未运行该开发分支的数据库按正常迁移流程升级。

## 本地覆盖

- 同 Agent 两个来源 Session 的相同正文独立记录；相同调用不重复外发；unknown 不重发。
- 真实 ingress round、正文与 pairing 核对；失败入站不能回传，重试后旧 round 不能继续授权。
- 两条投递消歧、使用前一条人类消息作为反馈原文；跨 Session 引用、改变已提交意图拒绝。
- 本地受理失败可从持久意图修复；DM 忙碌时排队，重复受理只派发一次，篡改正文拒绝。
- Room 精确 conversation / 原 Agent 私域路由，无自动公开或旧 Goal 归因。
- Automation exact producer 与权限版本复核；旧 run 状态保持。
- pairing 禁用后重新启用，旧 delivery 的回传资格仍失效。
- 原有好友私聊和 Room realtime 整包回归。

这些测试使用 SQLite、fake runtime / fake channel，不能证明真实 IM 平台验收或 PostgreSQL 运行结果。

## 部署后真实通道验收（待执行）

微信、飞书分别执行：

1. 同一 Agent 的 App 会话 A 发送审批材料到已配对手机，保存返回的 delivery_id；确认手机收到。
2. 手机回复明确修改意见，确认 IM 智能体通过已有工具回传，A 中出现带原文的反馈并继续处理。
3. App 会话 B 发送相似材料；手机只说“确认”时应按上下文确定来源，无法确定时提问，不能猜最近记录。
4. 先发修改意见、再回复消歧信息，验证返回的是修改意见而非只返回“第一份”。
5. A 忙碌时回传，确认排队，结束后只启动一次；工具重复调用不重复投递。
6. 重启后仍可查询旧来源；解除/改绑 pairing 或删除 A 后，旧记录不能回传到新会话。
7. 制造发送响应丢失，确认显示 unknown 且不会后台重发。
8. 回传成功不等于审批通过、任务完成或原 Automation run 再次执行；由原智能体结合任务决定后续动作。

不要为验收自动向实际联系人发消息；先使用用户指定的测试账号与会话。
