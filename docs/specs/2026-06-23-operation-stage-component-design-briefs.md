# Operation Stage 组件设计方案

日期：2026-06-23

这份文档先不画最终 UI。目标是把每个组件的设计定位讲清楚，再决定具体视觉稿。上一轮 demo 太像看板，问题在于它把工具结果摊平成卡片；Operation Stage 应该更像一个“用户可观察的智能体操作系统”：智能体在里面打开 app、切换窗口、执行命令、请求权限、生成产物，用户看到的是过程，而不是工具清单。

## 总体原则

- 用户不是在操作这些工具，而是在观察智能体如何操作。
- 每个组件都应该像一个真实软件 app，而不是一张统计卡片。
- 窗口之间要有主次关系：当前执行窗口最清楚，辅助窗口只保留上下文。
- 所有工具状态都落到统一语义：准备、执行中、等待权限、产出中、完成、失败。
- 不为了炫技做复杂动画；先让用户一眼看懂智能体正在做什么、用了什么、产出了什么。

## 0. Agent OS Shell

定位：所有组件的容器层，不是工具组件本身。

真实软件隐喻：macOS / Windows 桌面 + 任务管理器 + Dock。

用户要看懂的事：
- 智能体当前打开了哪些 app。
- 当前焦点在哪个窗口。
- 哪些任务正在后台运行。
- 哪些动作需要用户介入。

核心状态：
- 空闲：桌面干净，只显示当前目标。
- 执行中：Dock 有活动指示，当前窗口置顶。
- 多任务：后台窗口缩小但保持可见。
- 权限等待：系统级弹窗压到最前。
- 完成：桌面收束为交接摘要。

视觉原则：
- 桌面是舞台，不是仪表盘。
- 顶部系统栏只放运行状态、预算、时间、全局入口。
- Dock 放 app，不放工具名。
- 右侧可以有 Activity Center，但不能抢主窗口。

先不做：
- 不做真实可拖拽窗口。
- 不做完整文件管理器能力。
- 不做拟物过度的桌面皮肤。

## 1. Workspace / Finder

定位：文件系统和工作区上下文浏览器。

真实软件隐喻：Finder / VS Code Explorer。

用户要看懂的事：
- 智能体正在看哪个目录。
- 哪些文件被读过、改过、新建过。
- 文件和后续工具动作之间的关系。

核心状态：
- scanning：正在列目录或 glob 匹配。
- reading：打开某个文件。
- changed：文件已被编辑。
- created：新产物生成。
- ignored：被规则排除。

交互：
- 点击文件打开 Code / Document / Image 对应窗口。
- 文件行显示工具来源，比如 LS、Glob、Read、Write。
- 改动文件应该自动置顶。

视觉原则：
- 左侧目录树，右侧文件列表。
- 文件状态用细小标识，不用大面积颜色。
- 当前文件和当前执行工具要连起来。

先不做：
- 不做完整 diff。
- 不做复杂权限模型。

## 2. Code Editor

定位：代码读取和修改窗口。

真实软件隐喻：VS Code / Xcode diff editor。

用户要看懂的事：
- 智能体改了哪个文件。
- 改了哪几行。
- 修改是否已经保存。
- 修改后是否进入测试。

核心状态：
- reading：只读预览。
- editing：正在插入或替换。
- patched：补丁已应用。
- saved：写入完成。
- conflict：补丁无法应用。

交互：
- 左侧显示 changed files。
- 主区域显示代码和 diff。
- 右侧或底部显示这次 Edit/Write 的原因。

视觉原则：
- 代码窗口必须像真实编辑器，不能像卡片。
- 当前行、添加行、删除行清晰区分。
- 文件 tab 可以表达多文件切换。

先不做：
- 不做完整 IDE。
- 不做语法高亮全量覆盖。

## 3. Terminal

定位：命令执行和日志流窗口。

真实软件隐喻：Terminal / GitHub Actions logs / Vercel logs。

用户要看懂的事：
- 执行了什么命令。
- 当前输出到哪一步。
- 是否失败，失败在哪一行。
- 退出码和耗时。

核心状态：
- queued：命令等待执行。
- running：流式输出。
- success：退出码 0。
- failed：退出码非 0。
- killed：用户或系统终止。

交互：
- 支持折叠成功段。
- 失败行自动高亮。
- 可以切换 stdout/stderr。

视觉原则：
- 黑底终端保留真实感。
- 行号不是必须，时间戳更有用。
- 只在失败时强提示，不要每行都加颜色。

先不做：
- 不做可输入终端。
- 不做复杂日志搜索。

## 4. Browser / Web Evidence

定位：网页读取、外部证据和引用预览。

真实软件隐喻：浏览器 + 阅读模式 + 引用侧栏。

用户要看懂的事：
- 智能体访问了哪个网页。
- 抽取了哪些内容。
- 哪些内容被用于回答或决策。
- 来源是否可信。

核心状态：
- loading：正在抓取页面。
- extracted：正文已抽取。
- cited：引用已进入证据包。
- blocked：访问失败或需要登录。

交互：
- 地址栏显示来源。
- 主区域显示网页摘要。
- 右侧显示 citation cards。

视觉原则：
- 不要做成通用卡片列表，要像浏览器窗口。
- 网页正文要留白，让用户知道这是外部页面。
- 引用编号和最终回答保持一致。

先不做：
- 不做完整网页渲染。
- 不做登录态浏览器。

## 5. Task / Plan Board

定位：智能体计划和子任务进度。

真实软件隐喻：Linear issue view / job run checklist。

用户要看懂的事：
- 智能体把任务拆成了几步。
- 当前在哪一步。
- 哪些步骤完成、跳过或阻塞。
- 子任务输出是否已经合并。

核心状态：
- planned：计划已生成。
- in_progress：执行中。
- blocked：等待用户或外部结果。
- skipped：智能体判断不需要做。
- done：完成。

交互：
- 当前步骤高亮。
- 可展开查看对应工具调用。
- 结束时折叠成完成摘要。

视觉原则：
- 更像任务运行清单，不像项目管理看板。
- 一屏能扫完，不做横向 Kanban。

先不做：
- 不做拖拽排序。
- 不做多人任务协作。

## 6. Permission Center

定位：权限请求和用户决策窗口。

真实软件隐喻：系统权限弹窗 / 1Password 授权 / macOS security prompt。

用户要看懂的事：
- 智能体想做什么。
- 为什么需要权限。
- 影响范围是什么。
- 允许一次和始终允许的区别。

核心状态：
- requested：权限请求出现。
- waiting：等待用户选择。
- approved_once：允许一次。
- approved_always：加入策略。
- denied：拒绝。

交互：
- 系统级 modal，必须置顶。
- 展示原始工具名和人类可读解释。
- 决策后在 Activity Center 留记录。

视觉原则：
- 权限弹窗要克制，像系统安全提示。
- 风险信息优先于按钮。
- 危险操作不能只靠颜色表达。

先不做：
- 不做复杂策略编辑器。
- 不做批量授权。

## 7. Goal Console

定位：当前目标和预算状态。

真实软件隐喻：任务目标条 / run summary。

用户要看懂的事：
- 当前智能体目标是什么。
- 预算或上下文还剩多少。
- 是否完成或阻塞。

核心状态：
- active：目标进行中。
- near_limit：预算接近上限。
- complete：目标完成。
- blocked：连续阻塞。

交互：
- 常驻在系统栏或 Activity Center。
- 点击可展开目标历史。

视觉原则：
- 轻量，不应该像一个大 app。
- 更像 OS 状态模块。

先不做：
- 不做复杂 OKR 页面。

## 8. Automation Center

定位：计划任务、定时任务和自动化运行记录。

真实软件隐喻：cron monitor / GitHub Actions scheduled workflows。

用户要看懂的事：
- 自动化任务何时触发。
- 这次运行到哪一步。
- 是否已投递结果。
- 失败后怎么恢复。

核心状态：
- scheduled：已计划。
- running：正在执行。
- delivered：结果已投递。
- failed：运行失败。
- recovered：恢复完成。

交互：
- 任务详情展示 cron、时区、下一次运行。
- 运行记录按时间线展开。
- 失败任务显示 retry/recover。

视觉原则：
- 像自动化控制台，不像日历。
- 时间、状态、投递目标要清楚。

先不做：
- 不做复杂流程编排器。

## 9. Room / Message Console

定位：房间消息和定向消息投递。

真实软件隐喻：Slack message composer + delivery receipt。

用户要看懂的事：
- 智能体准备发什么消息。
- 发给谁。
- 是否已投递。
- 是否是公开消息还是定向消息。

核心状态：
- composing：生成消息。
- sending：发送中。
- delivered：已送达。
- failed：投递失败。

交互：
- 发送前可预览消息。
- 投递后显示回执。
- 定向消息显示目标用户。

视觉原则：
- 像消息窗口，不像表单。
- 消息正文是主角。

先不做：
- 不做完整聊天室。

## 10. Connector Console

定位：连接器调用调试台。

真实软件隐喻：Raycast extension detail / Postman-lite / API inspector。

用户要看懂的事：
- 调用了哪个连接器。
- 传了什么参数。
- 是否通过授权。
- 返回了什么结果。

核心状态：
- listing：列出连接器。
- preparing：准备请求。
- calling：远端调用中。
- success：返回成功。
- error：返回错误。
- permission_wait：等待授权。

交互：
- 左侧连接器和 action 列表。
- 中间 request/response。
- 底部显示 token、耗时、错误码。

视觉原则：
- 像 API 调试工具，但比 Postman 更轻。
- 原始 JSON 可见，但默认给摘要。

先不做：
- 不做完整 API client。
- 不做手动改参数。

## 11. Document Viewer

定位：文档读取、创建和更新。

真实软件隐喻：Google Docs / Notion read mode。

用户要看懂的事：
- 正在读哪份文档。
- 命中了哪些段落。
- 是否写入或追加内容。
- 文档链接和来源。

核心状态：
- loading：加载文档。
- reading：读取正文。
- highlighting：标注命中内容。
- writing：写入中。
- saved：保存完成。

交互：
- 主区域显示文档页面。
- 右侧显示 block outline。
- 命中内容可跳转。

视觉原则：
- 文档要像纸面或编辑器，不像数据卡。
- 高亮要克制，保留原文结构。

先不做：
- 不做完整富文本编辑。

## 12. Table Viewer

定位：表格、电子表格、多维表格的读写。

真实软件隐喻：Google Sheets / Airtable grid。

用户要看懂的事：
- 正在读写哪个 range。
- 哪些单元格发生变化。
- 表头和字段类型是什么。
- 是否批量提交成功。

核心状态：
- loading_schema：读取表头。
- reading_rows：读取行。
- editing_cells：准备写入。
- committing：提交中。
- committed：提交完成。

交互：
- 单元格变更高亮。
- 左上角显示 sheet/table 名称。
- 右侧显示变更摘要。

视觉原则：
- 像真实表格，不像 JSON。
- 行列坐标必须可见。

先不做：
- 不做复杂公式计算。

## 13. Knowledge Base

定位：知识检索、Skill 使用和引用关系。

真实软件隐喻：知识图谱 + 搜索结果面板。

用户要看懂的事：
- 智能体查了什么知识源。
- 哪些结果被采用。
- 引用之间是什么关系。
- 是否来自 Skill、文档还是记忆。

核心状态：
- searching：检索中。
- ranking：排序中。
- selected：选中引用。
- synthesized：生成摘要。

交互：
- 左侧查询和来源。
- 中间关系图或结果列表。
- 右侧引用详情。

视觉原则：
- 不要一上来做复杂大图谱。
- 默认结果列表，必要时展示关系。

先不做：
- 不做炫酷但难读的知识网络。

## 14. Image Studio

定位：图片生成、编辑和预览。

真实软件隐喻：轻量图片工作台 / Figma asset preview。

用户要看懂的事：
- 提示词是什么。
- 正在生成还是编辑。
- 产物路径在哪里。
- 哪张图被采用。

核心状态：
- prompting：准备提示词。
- generating：生成中。
- preview_ready：预览完成。
- saved：保存产物。
- failed：生成失败。

交互：
- 主区域显示图片。
- 侧栏显示 prompt、尺寸、文件路径。
- 可标记 selected asset。

视觉原则：
- 图片是主角。
- 元信息不能压过预览图。

先不做：
- 不做完整图片编辑器。

## 15. Map Viewer

定位：地点、路线和地理结果。

真实软件隐喻：Apple Maps / Google Maps route card。

用户要看懂的事：
- 起点终点是什么。
- 路线和耗时。
- 搜索到的地点是否正确。

核心状态：
- resolving：解析地点。
- routing：规划路线。
- result_ready：结果完成。
- ambiguous：地点不唯一。

交互：
- 地图主区域。
- 底部路线卡。
- 歧义地点需要用户选择。

视觉原则：
- 地图要像地图，不是列表。
- 路线卡比原始 API 重要。

先不做：
- 不做真实地图瓦片接入。

## 16. Ride Panel

定位：打车、路线和费用确认。

真实软件隐喻：滴滴 / Uber 下单流程。

用户要看懂的事：
- 车型和价格。
- 起终点。
- 是否即将下单。
- 是否需要用户确认。

核心状态：
- estimating：估价。
- confirm_wait：等待确认。
- ordering：下单中。
- assigned：已派车。
- cancelled：取消。

交互：
- 下单前必须弹出确认。
- 费用和目的地必须醒目。
- 状态按流程展示。

视觉原则：
- 像出行订单，不像 API 调用。
- 用户确认是核心，不要隐藏。

先不做：
- 不做真实支付或订单管理。

## 17. Handoff Summary

定位：本轮操作交接和证据包。

真实软件隐喻：run report / deployment summary。

用户要看懂的事：
- 完成了什么。
- 改了哪些文件。
- 运行了哪些校验。
- 下一步是什么。

核心状态：
- collecting：收集产物。
- summarizing：生成摘要。
- ready：可交接。
- incomplete：有未完成项。

交互：
- 点击证据打开对应窗口。
- 摘要分为完成、验证、风险、下一步。

视觉原则：
- 像一次运行报告，不像聊天消息。
- 证据链接必须具体。

先不做：
- 不做自动 PR 描述生成器，除非后续需要。

## 18. Generic Tool Window

定位：未知 MCP 或未分类工具的兜底窗口。

真实软件隐喻：通用 inspector。

用户要看懂的事：
- 工具来自哪个 server。
- 工具名是什么。
- 输入输出是什么。
- 为什么没有专用 UI。

核心状态：
- parsed：工具身份解析成功。
- running：执行中。
- output_ready：输出完成。
- unmapped：没有专用分类。

交互：
- 显示 server/tool/source。
- 输入输出可折叠。
- 常用后提示可以升级为专用组件。

视觉原则：
- 保持朴素，不能比专用组件更抢眼。
- 重点是可解释和可追踪。

先不做：
- 不为每个未知工具自动生成复杂界面。

## 第一批建议落地顺序

1. Agent OS Shell：先把桌面、系统栏、Dock、Activity Center 定下来。
2. Terminal：最容易做出真实执行感。
3. Code Editor：最能体现智能体在工作。
4. Permission Center：产品信任感关键。
5. Connector Console：Nexus 自己的能力核心。
6. Handoff Summary：让用户知道本轮结果。

其他组件先用 Shell + Generic Tool Window 承载，等真实使用频次上来再细化。
