# Windows 可信启动器：部署与授权设计

状态：non-normative，待实现与 Windows 原生验收。本文给出后续实施方向，不能据此声明当前产品已有服务端沙箱。当前合同仍是 `docs/specs/desktop-sandbox-spec.md`。整个 Goal 还包括 macOS、文件工具、审批、自动审核与旧功能回归。

## 决策依据与方向

现有 App 安装器在 `scripts/desktop/package-windows-app.ps1` 使用 `PrivilegesRequired=lowest`，安装到 `{localappdata}\Programs`。`SidecarSupervisor.BuildStartInfo` 以当前用户启动普通后端；当前没有受保护的机器级启动服务。现有签名流程允许普通开发包跳过签名。不得把该用户可写安装目录的可执行文件作为高权限服务入口。

同账号 runner 的原生探针已证实 WRITE_RESTRICTED 令牌可获取 runner 线程的模拟身份权限。完整受限令牌阻止了这些权限，但当前无法读取系统 CLR DLL，并且正常后代 CreateProcess 仍失败。文件读取、令牌对象访问和 stdio 复制的成功不能替代完整进程验收。具体提交与运行链接见本目录 README 的证据记录。

后续实施采用**可信 broker 与命令账号分离**的方向：普通 App/后端维持当前用户身份；可选受保护 broker 承担跨账号创建；命令始终以独立普通执行账号和受限令牌运行。不能把同一账号的两个进程称为身份分离，也不能从当前失败测试推断该方案已经可用。

不以修改整棵 Windows/System32、系统注册表或增加宽泛 restricting SID 作为隐式兼容修复。当前完整受限令牌组件继续保持未接入状态。只有不同身份下的文件、网络、进程/线程/令牌与后代测试全部通过，才能确定 broker 路径的最终令牌模式；不得为同账号路径恢复已知有缺口的模式。

## 身份和部署

| 主体 | 可做的事 | 禁止的事 |
| --- | --- | --- |
| 普通桌面 App / Nexus 后端 | 保留现有用户目录安装、升级和权限决策；发起可选组件设置 | 整体提升到管理员身份；自行声明 broker 已验证 |
| 独立设置程序 | 经用户发起的系统提权安装、修复、升级或卸载受保护组件 | 从用户可写路径配置长期高权限服务；信任请求正文指定的 owner |
| 可信 broker | 核验客户端身份和批准的执行描述，创建/取消受限进程，记录精确回执 | 以自身身份运行命令、脚本、插件、用户 DLL 或用户可控启动钩子 |
| 普通执行账号 | 在授予的文件/网络边界内执行命令和后代 | 访问 broker 对象、服务配置、凭据、批准记录或其他 owner |

机器级服务是实施候选，LocalSystem 只可用于可信创建与资源管理，不是命令身份。必须在原生验证中证明所需权限、Session/桌面隔离和原子 Job 绑定；不能把服务的高权限传给模型。broker 不加载工作区、用户 Skill、Provider 或动态 MCP，不使用 shell 解析控制请求。

受保护程序采用固定机器安装位置和不可变版本目录，只有受信任安装主体可更新。正式组件必须验证发布者、内容完整性与兼容版本；普通 App 的 SkipSigning 不得成为高权限组件的生产旁路。服务可执行路径必须明确引用受保护文件，普通用户不能修改服务配置或替换路径祖先。哈希来自可信发布元数据，不能把旁边可同时修改的 hash 文件当作签名。

新增机器级持久状态是现有桌面状态根合同的**待实现扩展**：不能直接混入可迁移的用户 `.nexus` 数据并当作高权限权威。落地前须在唯一当前规范与 AGENTS 状态根合同中明确机器权威的路径、所有者、备份与清理规则。用户状态迁移不得搬走服务二进制、机器凭据或伪造执行回执。现有 Connector 的明文凭据兼容回退不能复用于执行账号密码。

## 安装、更新和卸载链路

1. 用户启用受限模式时检查平台、组件版本、签名、机器安装和执行账号状态；缺失时提供明确设置结果，不启动命令、不切换完全访问。
2. 系统提权仅用于设置程序。安装时从经验证的发起进程取得用户身份，并处理 UAC 使用另一管理员账号的情况；不得把提权后的账号误当成原始 owner。
3. 在受保护位置验证并暂存完整版本，配置服务 ACL、执行账号和凭据存储，运行身份/文件/网络自检后才提交 ready。账号存在或服务存活都不等于 ready。
4. App 更新仍走当前普通用户安装链。broker 独立协商版本；不兼容时拒绝受限执行并请求修复，不能自动回退。broker 更新先停止新准入，收口或等待已有 Job，再切换版本；失败保留可诊断的旧版本状态。
5. 卸载先拒绝新请求、终止并核验其所有 Job 为空，再清理本组件拥有的账号、ACL/WFP 资源、凭据和机器注册。保留用户工作区；不能凭路径名删除不属于本次安装的账号或文件。
6. 策略禁止安装、用户取消 UAC、更新失败或组件损坏只影响受限模式的可用性。完全访问保持现有普通用户执行路径，不通过服务获得管理员权限。

## 通信与批准

- 使用本机命名管道、封闭版本化消息、长度上限和截止时间。服务器身份由受保护安装事实与活进程句柄核验；客户端身份由内核取得，不能采用消息中的 PID/SID 声明。
- 现有管道组件用于宿主验证独立 runner，不能原样当作 broker 验证客户端的完整实现。双方都要验证角色、owner 和安装代次，句柄不可泄漏给命令账号。
- 宿主把 owner/session/round/tool、策略版本、命令/参数、cwd、环境和资源授权绑定为一个不可变执行描述。参数和策略都受摘要约束；同 request ID 不得换正文重用。
- 工具审批仍由现有领域权限处理。沙箱越界批准是另一项精确执行授权；批准前不扩大权限，不持久化通用越界规则。自动审核只能消费可信审批上下文，不能安装组件、代替 UAC、覆盖强制拒绝或伪造人工决定。
- broker 只接受明确允许的受限执行类型。完全访问或沙箱外重跑也不得请求以 broker 的高权限身份执行；若要保留用户原有身份，必须走单独已批准的普通用户执行路径。
- 网络授权仍按目标连接绑定原命令和策略代次；操作系统网络限制先建立，代理审批不能成为可绕开的唯一网络边界。

## 创建、取消与结果不明

身份和批准核验 → 持久准入回执 → 准备文件/网络租约 → 原子创建到 Job 且主线程悬挂 → 核验实际令牌与 Job → 持久化准备恢复事实 → 恢复线程 → 记录执行/终态 → Job 空确认 → 回收租约。

“准备恢复”之后崩溃而缺乏终态时，按可能已执行处理；不能因为缺少 resumed 回执便重放。相同请求重连只能查询或取消已有实例，不得再创建。新授权、策略切换或过期审批不能复活旧实例。取消确认必须来自精确 Job 的退出证据，进程句柄关闭或 IPC 断开不是完成证明。未知结果的历史不得按简单 TTL 清掉后重新接收同 request ID。

## 仓库改造归属与验收

| 位置 | 后续实现责任 | 必须保留的回归 |
| --- | --- | --- |
| SDK 原生沙箱组件与独立 broker 入口 | 明确底层包边界，复用令牌、Job、桌面、句柄和管道组件；补身份分离、文件/网络执行与回执 | 进程/线程/令牌获取拒绝，正常子孙进程、取消、命令与运行库兼容 |
| Bridge | 能力协商、精确调用身份、批准结果与取消传递 | 不支持时明确失败；不自动重复有副作用的请求 |
| Nexus runtime / 权限服务 | 可用性、策略代次、领域审批与自动审核；完全访问切换 | DM/Room/后台任务隔离，迟到批准拒绝，现有领域拒绝保持 |
| desktop/windows 与 scripts/desktop | 可选设置 UI、受保护组件发布、独立升级/修复/卸载 | 原普通用户安装、App 更新、状态根迁移及完全访问不回退 |
| macOS 与 Linux 路径 | 按原 Goal 继续原生工具覆盖和隔离回归 | 不把 Windows 服务或权限模型注入现有平台 |

落地前先验证不同身份 broker 的真实启动、系统/用户运行库兼容、子孙进程与 IPC 身份拒绝；然后实现受保护安装和持久回执，再接入文件/网络与产品审批。Windows hosted CI、Windows 10/11 安装包实机验收、macOS 实机以及 Linux 多用户隔离分别记录，不能相互替代。

参考：[Microsoft 服务访问控制](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights)、[LocalSystem 权限与用户会话区别](https://learn.microsoft.com/en-us/windows/win32/services/localsystem-account)。以上权限事实用于设计约束，不代表建议让模型拥有服务身份。
