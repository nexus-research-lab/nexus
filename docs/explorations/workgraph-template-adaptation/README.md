# WorkGraph 模板参数化与 Room 自适应探索

> **状态：探索中（non-normative）**

## 背景

Nexus 当前已经能够从完成态 managed WorkGraph 提取结构草图，经用户确认后保存为命名工作图，并通过直接 Slash 指令在其他 Session 中复用。复用时只继承抽象的业务节点、依赖和验收语义；系统为当前请求创建新的 Execution、Plan 和 Work Item identity，实际拆分与分工仍由 Agent 根据当前 DM 或 Room 环境重新规划。

这种设计适合 Room：不同 Room 的成员数量、能力、权限、可用状态和协作关系可能完全不同，同一命名工作图不应机械复制成完全相同的运行 Plan。

待探索的问题不是“工作图能否沉淀”，而是：**在保留 Room 自适应规划的前提下，是否需要让模板中的可变输入和不可弱化约束更加明确。**

当前命名工作图会把保存的节点、依赖、交付和验收语义作为模型侧规划约束提供给 Agent；新 Plan 仍接受通用 Plan parser 和 materialization 校验。服务端目前不会独立比较“模板结构”和“最终 Plan”，因此不能声称已由服务端逐条证明模板契约得到保留。本文探索的结构保真边界，是指是否值得增加更显式的表达或验证，不是补齐尚未存在的沉淀能力。

本文使用以下简写：

- **命名工作图**：用户从完成图中沉淀、可通过 Slash 复用的抽象业务蓝图；
- **managed WorkGraph**：由权威 Execution 的 active Plan 和非空 Work Item 集合形成的受管工作图；普通 runtime-only 图或 Goal-only 会话不属于可提取来源；
- **Plan**：某个具体 Session 中实际执行的一版工作图；
- **直接 Slash**：以 `/<name> 当前请求` 形式调用命名工作图；
- **coordinator**：当前 DM 的执行 Agent，或 Room 中有权组织本次 WorkGraph 的协调 Agent。

## 初步原则

以下原则是评估候选方案时不应突破的边界，不代表已经决定具体协议：

1. 命名工作图仍是可复用的业务蓝图，不是可直接执行的固定 Plan。
2. 复用时必须重新读取当前 Session、Room、Agent、权限和任务上下文。
3. 模板可以约束必须保留的阶段、依赖、复核边界、最终交付和最低验收标准，但不默认固定节点数量或负责人。
4. 角色优先表达责任约束，例如“需要独立审核者”，而不是永久绑定某个 Agent ID。
5. 参数只用于减少真实歧义，不把自然语言请求全部改造成表单或 DSL。
6. 不新增第二套 Workflow runtime、Plan 状态机或脚本执行权威。
7. 任何增强都必须继续通过现有 Execution/Plan authoring、校验和 materialization 边界。

## 可能的优化方向

### 1. 轻量参数提示

若后续采用参数提示，命名工作图可以选择性声明少量有业务意义的输入，例如：

- `topic`：本次调研或交付主题；
- `output_language`：交付语言；
- `delivery_format`：报告、代码、表格或其他交付形式；
- `constraints`：用户明确给出的时间、范围或合规限制。

这些字段可以帮助 Composer 和 Agent 发现缺失输入，但是否采用类型、默认值、必填校验或输入面板尚未决定。Slash 后的自然语言仍应是主要入口。

### 2. 自适应角色约束

若后续采用角色约束，模板可以表达协作意图，例如：

- 某个阶段需要与生产者不同的独立审核者；
- 最终整合必须由当前 coordinator 承担；
- Room 人数充足时允许把独立研究方向并行分配；
- Room 人数不足时允许合并生产责任，但不得取消必要的独立复核。

这些角色应是规划约束，不是保存时绑定的长期成员身份。复用时仍由 Agent 根据当前 Room 成员和有效权限形成具体 Plan。若硬约束无法满足，系统不能静默降级；究竟应停止创建、仅为本次请求征得用户放宽，还是生成新的模板版本，仍是待决问题。

单 Agent DM 也属于必须考虑的场景。如果模板要求真正独立的审核者，而当前 Session 没有可验证的第二责任主体，不能把同一 Agent 的自检自动解释为已经满足独立复核。

### 3. 结构保真边界

若后续采用结构约束，模板可以区分：

- 必须保留的关键阶段；
- 可以按任务和 Room 规模扩展、合并或省略的协作节点；
- 不得削弱的 hard dependency；
- 必须保留的 terminal 交付；
- 最低验收条件和独立复核要求。

目标是约束规划结果的业务完整性，而不是要求每次实例化产生完全相同的图。

关键阶段是否允许合并到同一个 Work Item、节点合并后如何保存 dependency 语义，以及模板节点与新 Plan 节点如何建立可验证映射，目前都没有定案。

### 4. 可解释的实例化结果

复用命名工作图后，可以考虑从最终 Plan 和所用模板版本派生一份紧凑的只读适配说明：本次识别了哪些显式参数、保留了哪些关键结构，以及因为当前 DM 或 Room 条件做了哪些拆分或合并。

这份说明若存在，只用于用户理解和审计展示，不能成为绕过 Plan 校验或运行权限的新权威来源。Execution、Plan、Work Item、Assignment、Attempt、Submission、Review 和 Acceptance 仍分别承担当前运行与交付证据。

## 示例

假设未来允许一张“调研、复核、整合”的命名工作图声明：

- 本次主题是可变输入；
- 证据收集、独立复核和最终整合是必须保留的阶段；
- 最终交付必须经过复核；
- 研究分支数量可以适配 Room。

在只有两个 Agent 的 Room 中，规划结果可以是：

1. Agent A 负责调研与最终整合；
2. Agent B 独立复核；
3. 复核通过后解锁最终交付。

在有五个 Agent 的 Room 中，规划结果可以是：

1. 三个 Agent 并行调查不同证据方向；
2. 一个 Agent 独立复核汇总结果；
3. coordinator 完成最终整合。

两张 Plan 的节点和负责人不同，但都保留同一命名工作图的关键业务结构。

## 暂不纳入的方向

- 把命名工作图直接机械编译为固定 Plan；
- 永久保存具体 Agent ID 作为跨 Room 负责人；
- 要求不同 Session 生成完全相同的节点数量和拓扑；
- 为参数化引入通用表达式语言或任意脚本；
- 借参数化同时引入 live Assignment/Attempt carry；
- 借模板控制规则引入第二套运行、恢复或调度状态机。

## 待回答的问题

1. 哪些真实复用场景因为当前纯自然语言适配而产生了可观察的问题？
2. 参数应只是 Agent 可见的提示，还是需要服务端类型与必填校验？
3. 哪些结构属于不可弱化约束，哪些只是建议？
4. “独立审核者”等角色约束在人数不足的 Room 中应如何处理？
5. 是否需要在创建 Plan 前向用户展示适配结果，还是沿用当前直接执行体验？
6. 是否需要记录模板版本与本次 Plan 的适配差异，记录到什么粒度才不会形成第二套真相？
7. 当前 Draft revision 和命名工作图 version 是否已经满足审计需求？
8. 参数化带来的稳定性收益是否足以抵消配置、迁移和界面复杂度？

## 何时值得继续设计

只有出现以下至少一种可验证需求时，才值得进入正式方案阶段：

- 同一命名工作图重复使用时经常丢失关键阶段或验收条件；
- 用户频繁重复补充同一组结构化输入；
- Room 中的生产者与审核者责任经常分配错误；
- 用户需要在执行前确认不可弱化的流程约束；
- 审计要求必须解释命名工作图如何适配为本次 Plan。

如果这些问题没有真实出现，继续保持当前“抽象结构 + Agent 自适应规划”更简单，也更符合 Room 的动态协作模型。
